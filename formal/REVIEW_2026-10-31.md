An adversarial read of origin/lang at 48f28df8b against TRUSTED_BASE.md,
SEMANTIC_DECISIONS.md and the top theorems. Read only: nothing was built or
run. The documentation-only findings (compound-assignment order, the
`undefinedTrap` row, the free-choice list, `DataEq`, stale numbers) are
fixed in TRUSTED_BASE.md and ROADMAP.md, and the xmm finding (6) in the
x86 model, each in its own commit. The others are kept here until they are fixed. Each entry:
the claim, why it is weak, a scenario, and the planned fix.

## 1. No output guarantee unless the call returns; `Faults` admits divergence

`Faults s` (`Mini/StepDet.lean`) says every run that stops, stops at a
fault, so a run that never stops satisfies it. The output equations
(`outputOf 1/2`) are only in the branch where the call returns
(`process_exits`, `compileSource_correct`); `compileSource_stops` and the
short-stack branch say nothing about the trace. Scenario: `write_stdout("ok\n");
assert(false);` may print anything before it faults, or loop forever; a
`while (true) { write_byte(..); }` server's output is unconstrained. Planned
fix: a fault within a bounded number of steps, and a prefix theorem (the trace
at a fault is a prefix of Core's output at the trap), then a trace semantics
for runs that never stop, as CompCert has.

Not started: this is the most serious open finding, but it needs a new
invariant on each layer of the stops proof. `Faults` becomes "stops at a
fault whose trace satisfies P". The machine-to-mini relation (`Rel`,
`StopsCorrect`) carries trace equality to each fault point. `Stops` in the
mini semantics (`Mini/Stops.lean`, `EvalStops.lean`) records, at each
checked trap, Core's world at the corresponding trap (`HeapCorr.out` and
`.err` already relate the two). That is several thousand lines of
simulation, more than one session.

## 2. `typeMismatch` is undefined, and nothing proves accepted programs avoid it

`undefinedTrap` (`Mini/Fails.lean`) counts `typeMismatch` as undefined, on
the claim that a typed program reaches it only through an invalid bit pattern
in raw memory (SEMANTIC_DECISIONS.md, "Traps in compiled code"). That is not
proved: `compileSource_wellTyped` gives typing, but no theorem says a
well-typed Core program never reaches `typeMismatch` (only `func_safe` and
`driver_safe`, for the self program). Scenario: a reading or `toCore` error
that leaves a local unbound on one path makes Core's run `typeMismatch`
there, and the `_behaviour` theorems then allow any binary behaviour on it.
Planned fix: a progress theorem for programs `compileSource` accepts, raw
memory aside (generalising `driver_safe`), or make `typeMismatch` a checked
trap. Fixed on review-fixes for programs without raw memory:
`Mini/ShapeStep.lean` proves that a well-typed Core program whose bodies
avoid raw memory, and whose host functions are the lowered services, never
traps with `typeMismatch` from a typed state (`evalExpr_ne_typeMismatch`, by
store typing and value shapes, induction on fuel). `Mini/ShapeSource.lean`
applies it to `compileSource`: for a `SrcProgram.RawFree` program,
`call_ne_typeMismatch`, and `compileSource_behaviour_rawFree`, whose
undefined trap is never `typeMismatch`. Programs with raw memory (raw
slices, `load_byte`, `store_byte`, `alloc`, `dealloc`, `slice_stride`) still
have the escape hatch.

## 3. Standard input from a pipe: the model does not apply and input is lost

`Kernel.read` always delivers `min(rdx, remaining)`, and `host_read_code`
(`compiler.lani`) ends its loop on the first short read, which Core's
`read_stdin` would mean is the end of the input. Pipes and terminals return
short reads routinely, so for `cat big | prog` no input stream makes the
model match the kernel, and `read_stdin(buf, 1000000)` returns about 64 KiB.
TRUSTED_BASE.md section 8 says the code "would still be right" on a short
read; it is not. Fixed on review-fixes: the loop reads until `len` bytes or a
0 return, the model's `read` delivers any `0 < k ≤ min(rdx, remaining)` (0
only at the end) by a schedule of read limits fixed at the start
(`Io.readLimits`), and the sentence is gone.

## 4. Exit status unconstrained for unit, empty and padded results

The status is the last result slot (`process_exits`). `HoldsAt.unit` holds
any bits, an empty struct has no slots, and an enum constrains only its
variant's payload slots, so its last slot may be padding. Scenario: `fn
main() { .. }` may exit 1; `main -> Option<i32>` returning `None` exits with
garbage. Planned fix: the startup or a unit return sets the status to 0,
and the status is stated per result type.

## 5. The self-host theorems hold of a binary that always crashes or loops

`compileSource_outcome_from` (`Mini/SourceOutcome.lean`) drops the short
stack condition, so `selfCompiler_outcome`, `selfHost_fixpoint` and
`selfHost_outcome` conclude `Faults s ∨ returns` with no condition on the
fault. It also covers checked traps of `w` (a compiler `assert`, an index
out of bounds) and Core divergence, not only "out of stack, heap or output
room" as `SelfHost.lean`'s docstring says. That `B` terminates and returns
itself is the gate step `self-host-fixpoint`'s evidence, not a theorem.
Planned fix: keep the stack, heap and room conditions on the fault branch
and prove `w` terminates, or reword the docstrings.

Step 1 done on review-fixes: `compileSource_outcome_reason`
(`Mini/SourceOutcome.lean`) is `compileSource_outcome_from` with the reason
for a fault kept. The compiled call faults only when Core's call fails at
every fuel (it diverges, stops at a checked trap, or ends with the heap past
the limit), or when Core's call completes within the limit and the window is
below `binary.stackNeed depth`. Step 2 still to do, once the certificates
are regenerated (the Faithful modules do not build on review-fixes before
that): `selfCompiler_outcome`, `selfHost_fixpoint` and `selfHost_outcome`
use `compileSource_outcome_reason`. Their fault branch then becomes "Core's
run of `w` fails at every fuel, or it completes and the window is short". A
binary that always crashes no longer meets them for any input whose Core
run of `w` completes. Step 2 done on f12: the three conclude `SelfFaults`
(`SelfCompiler.lean`), Core's run `selfRun` failing at every fuel or
completing with the window short. Step 3: prove that run completes (a fuel bound for
`w` from the input size), or say in the docstrings that it is the gate's
evidence.

Step 3 plan (not started; it cannot be done in `Lanius/Mini` alone). The
Lean front end and compiler are total already: every recursion of
`frontend.lani` and `compiler.lani` takes an explicit fuel argument or
descends a list, and the driver's fuels come from the input size (the
lexer's is `length + 1`, `lexSource_eq` in `LexCorrect.lean`). What is
missing is Core's side. The certificates and `call_sim` only go backward
(a completed Core call means its pure call means the extraction), and no
theorem goes forward. Three pieces:

- (a) Pure calls complete: `pcall prog prims fuel c ps = some w` for every
  fuel past a bound in the arguments' sizes. Prove it with a syntactic
  termination check on `SrcFunc` bodies, next to `PureFunc` (every call to
  a function of the same group passes a smaller fuel argument or a proper
  sub-value of a list or tree argument), a generic `pcall_complete` lemma
  over that check, and one `decide` for `prog`.
- (b) A forward simulation from pure calls to Core calls, the converse of
  `call_sim` over `Faithful/Sim`: a pure call that completes, on arguments
  `VRels` relates, gives a Core run of the same call that completes at
  some fuel, with `Inv` kept and the heap grown by a bound. The heap bound
  is what `selfHeap`'s limit must then cover.
- (c) In `SelfCompiler.lean`: (a) and (b) on `w` with
  `compileSource_outcome_reason` leave a fault only when the stack window or
  the heap limit is short.

Both (a) and (b) live in `Lanius/Faithful`, so they wait on regenerated
certificates. Of the front end, only (a)'s check on the lexer and parser
functions could come first. `Faithful/Pure.lean` and `Sim/Check.lean`
build without the certificates.

The size of (a), from a count over the sources: `frontend.lani` has 1284
functions, 153 of them self-recursive, 96 of those without a fuel
argument. `compiler.lani` has 489 functions, 105 of them self-recursive,
104 without fuel. The check must therefore accept three kinds of descent:
`minus(fuel, 1)` under an `if (fuel == 0)` return, a sub-value bound by a
`match` on the argument (`compile_expr` on its tree), and a counted-down
number (`pow2`, `slot_range`). It must also accept mutual recursion, with a
rank per strongly connected group of the call graph.

Piece (a) status. `Sim/Term.lean` holds the check, a `Bool` over `SrcFunc`
bodies against untrusted annotations (`TermInfo`: per function a rank, the
argument positions whose largest size must fall, and a sub-rank within a
group). A call inside a group must lower the rank, or keep it and make the
designated arguments smaller (or keep their size and lower the sub-rank).
The size classes cover all three descents: match payloads and fields;
`minus(x, d)` with `1 <= d <= k` after an `x == 0` or `x < k` guard; and
values carried through boxing prims. `Sim/TermSound.lean` proves
`pcall_complete` once over the check: under `TermOk`, every call of an
annotated function settles, so past some fuel `pcall` gives one answer.
It uses the standard axioms only and adds nothing to the trusted base.
`tools/term_gen.lean` computes the annotations (SCC ranks, then a search
over argument positions) and writes `Gen/SelfTerm*.lean`, one
`decide +kernel` per function in 48 chunks. `settles_grammar`,
`settles_compile_words`, `settles_lex_source` and `settles_validate_files`
cover 1889 functions, and `lake build Lanius.Faithful.Gen.SelfTerm` takes
25 s. Gap: `fl_add` and `fl_less` recurse on two bit lists at once (calls
such as `f(empty(), tail(y))`), so no single-argument maximum falls. They
need a sum measure in the check, or a rewrite of the source. They and the
108 functions that reach them, `front_end_words` among them, are not
covered yet. The settled answer can be `none`: an evaluation error, or a
form with no pure meaning. (b) must rule `none` out from the Core side, or
carry it.

## 6. `State.syscalled` zeroed the xmm registers (fixed)

`State.syscalled` built a new `State` without `xmm`, which took the default
`fun _ => 0`, while Linux keeps xmm across a syscall and TRUSTED_BASE.md
said every other register is kept. It was benign for the current code (each
float operation loads xmm0 and xmm1 from general registers first), but a
real run with a float operation before a syscall was not a model run. The
fix: `xmm := before.xmm`.

## 7. stdout and stderr are not ordered relative to each other

Core's world keeps `standardOutput` and `standardError` as separate lists,
and the theorems relate only `outputOf 1` and `outputOf 2` of the trace.
Scenario: Core writes "A" to stdout, then "B" to stderr; the trace `[write 2
"B", write 1 "A"]` meets the theorem, and under `2>&1` the user sees "BA".
Planned fix: one ordered event log in Core's world, equal to the trace.

## 8. `Loaded` reads four header fields; the others are unchecked

`Loaded` (`Mini/Process.lean`) reads `e_entry`, `p_vaddr`, `p_filesz` and
`p_memsz` only. Whether Linux leaves a `Loaded` state depends also on
`e_type` (ET_DYN is relocated), `e_phoff`, `e_phnum`, `p_type`, `p_offset`
and `p_flags`, which the untrusted `elf_header`/`elf_program_header` write.
They are right today, but TRUSTED_BASE.md section 8's "a wrong header could
not make the theorem easier" overclaims. Planned fix: add equations for
those fields to `Loaded`.

## 9. Core and laniusc disagree

Arithmetic, division and shift guards and casts agree. They differ on:

- `for i in a..n` with `i` assigned in the body: the reading makes `i` a
  fresh copy each iteration, laniusc's loop variable is the counter
  (`loop_recipe.slang`), so `for i in 0..10 { i = i + 5; }` runs 10 times
  against 2;
- `let x: T;`: Core traps `uninitializedLocal` on a read, laniusc
  zero-fills (`docs/compiler-semantic-contracts.md`); the reading rejects
  the form;
- `a[i] = e` out of bounds: Core checks before `e`, laniusc after, so
  `a[5] = noisy();` prints under laniusc only;
- `for x in arr` with the body writing elements: Core iterates a copy,
  laniusc loads live;
- traps: laniusc exits 101-104, the verified compiler raises SIGILL or
  SIGFPE;
- struct literal fields out of declaration order (Core's elaboration order;
  the reading requires declared order) and unbounded `n..` ranges (laniusc
  stops at MAX).

Planned fix: decide each in SEMANTIC_DECISIONS.md, then change laniusc or
Core to match.

## 12. Kernel model assumptions that are not listed

`write` and `read` on a standard stream the parent left `O_NONBLOCK` can
return `EAGAIN` or a short count; `getrandom` needs Linux 3.17 and no
seccomp filter denying it; a negative error return would be folded into the
read loop's pointer and count. Planned fix: list these in TRUSTED_BASE.md
section 8.

## 13. The hash gate detects accidents, not every change

Statement hashes are 32-bit, non-cryptographic `Expr.hash`, and Lean's
`Hashable Nat` reduces modulo 2^64, so literals 2^64 apart collide
(suspected, not checked). Planned fix: say so in TRUSTED_BASE.md, or hash
the pretty-printed statements and definitions with SHA-256.

## Front end against laniusc (second reviewer)

Findings of the front-end reviewer, comparing the reading (`frontend.lani`,
`Mini/Reading/`) with laniusc on the same text.

### F1. The `for` range variable is a copy in the reading, the counter in laniusc

The reading turns `for x in a..n { body }` into `let c = a; let e = n;
while (c < e) { let x = c; c = c + 1; body }` (`for_of`, `for_range`), and
`x` is an ordinary assignable local, so `x = ..` in the body does not touch
`c`. laniusc's loop recipe (`loop_recipe.slang`, `direct_range_ops`) stores
`binding + 1` back into the binding, which is the counter, and its checker
lets a `for` binding be assigned. Scenario: a loop that counts its runs and
does `x = x + 1` in the body counts 10 under the reading and 5 under laniusc.

Fixing: the front-fixes branch.

### F2. `a[i] = f()`: the bound is checked before `f()` in Core, after it in laniusc

The reading gives `MSetIndexEval`, Core's assignment, which resolves the
place and checks the bound before it evaluates the value (SEMANTIC_DECISIONS,
"Traps in compiled code"). laniusc's indexed store is one operation on
(array, index, value), and its guard is emitted at the store
(`safety_emit.slang`), after the value is computed. Scenario: `a[5] =
noisy();` on a two-element array prints `noisy()`'s output under laniusc and
nothing under Core before the trap.

Fixing: the front-fixes branch.

### F3. A module file with only traits, externs or imports is not a module

`is_module` (`frontend.lani`) counts types, functions, constants and
aliases only, and `item_decls` gives no declarations for traits, non-host
externs, aliases with a `where` clause or imports, so an `import m;` of a
module holding only those is read as an item import or rejected. laniusc
builds its module table from module records, and a module wins over an
item when the whole path is a module (`05_resolve_imports.slang`).

Fixing: the front-fixes branch.

### F4. Host bindings: error results and single reads and writes

`write_byte` to a bad handle returns -1 in Core (`World.lean`) and in the
verified compiler, while laniusc's runtime returns the raw syscall result
(-9, `EBADF`; `runtime_abi.slang`). laniusc's `write_stdout` and
`read_stdin` make one `write(2)`/`read(2)` and return its count, short on a
pipe, where Core and the verified compiler write everything and read until
the count or a short read. This needs a Core decision on what host results
mean; short reads are also finding 3 above.

Fixing: open (needs a Core decision).

### F5. A payload binder spelled like an imported variant

`binder_of` (`frontend.lani`) reads any plain name in a payload pattern that
is not in the current module's globals as a binder, so a name that is a
variant of an imported module binds. laniusc resolves such a pattern to the
imported variant, a nested variant pattern, with no exhaustiveness check
(`10m_bind_match_patterns.slang`; the laniusc side is not fully traced, so
suspected). Scenario: `match o { Some(None) -> .. }` with `None` imported
binds a value named `None` in the reading and tests for `None` in laniusc.

Fixing: F11b.

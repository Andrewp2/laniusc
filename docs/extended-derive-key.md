# Derive a key from binary input

`sample_programs/library/derive_key.lani` streams binary standard input through
HKDF-SHA256 extraction, then calls `ext::hkdf_sha256::expand`. It uses fixed
packed stack buffers and allocates no heap storage.

```text
derive_key OUTPUT_BYTES SALT_HEX INFO_HEX
```

`OUTPUT_BYTES` is an unsigned ASCII decimal value from 0 through 8160. Each
argument is limited to 512 ASCII characters. Salt and info contain pairs of
hexadecimal digits, accept either letter case, and represent at most 256 bytes
each. Pass an empty argument for an empty salt or info. The program rejects
invalid arguments before reading standard input.

For example, the first [RFC 5869 SHA256 vector](https://www.rfc-editor.org/rfc/rfc5869#appendix-A.1)
uses 22 input bytes equal to `0b`, output length 42,
salt `000102030405060708090a0b0c`, and info `f0f1f2f3f4f5f6f7f8f9`.

## Data and limits

The extractor feeds each actual read into `ext::hmac_sha256::State` with the
decoded salt as its key. Its 32-byte result is the expansion PRK. Empty salt
has the HMAC padding behavior of a zero-filled key, as required by
[RFC 5869 extraction](https://www.rfc-editor.org/rfc/rfc5869#section-2.2).
The program calls the library expansion function with the decoded info and
requested output view; it does not implement another expansion loop.

Input may contain arbitrary bytes, including NUL, and is limited to 1 MiB.
Reads use a packed 1024-byte buffer. At the exact limit the program makes a
one-byte probe: EOF permits derivation; an additional byte fails. Zero output
length still consumes and validates the complete input. The common budget is
131,072 read/write attempts, including attempts interrupted by a signal.

After observing EOF and completing expansion, the program writes lowercase
hexadecimal followed by one newline. Zero output bytes produce just the
newline. The packed output view is at most 16,321 bytes. No output appears
before derivation finishes. A later write error can leave a confirmed prefix
on standard output. The process ignores SIGPIPE so a closed pipe returns an
I/O failure status. It does not flush or close borrowed descriptors.

| Status | Meaning |
| --- | --- |
| 0 | Complete output written |
| 2 | Invalid command line |
| 3 | Host I/O failure, invalid I/O count, or zero-progress write |
| 7 | Input, derivation, or shared call-budget limit |

This example accepts input keying material; it makes no password-processing
claim. Use HKDF within the input and context requirements of its calling
protocol.

## Verification

The accepted target is **x86_64 Linux native ELF generated by the GPU
compiler**. This evidence covers native execution, not user GPU kernels or
other targets. The focused driver is
[`extended_derive_key_execution.rs`](../tests/extended_derive_key_execution.rs).

| Gate | Accepted evidence | Elapsed |
| --- | --- | ---: |
| Fresh Rust driver build | Build after correcting the trace parser | 1.33 s |
| Application gate | One strict ELF, 51 native cases, 18 independent model inputs | 11.30 s |

The independent Python `hmac`/`hashlib` model is anchored by RFC 5869 SHA256
cases 1, 2 and 3. Execution also covers binary SHA block/read boundaries,
empty and maximum output, 256-byte salt/info, actual EOF at the 1 MiB input
limit, an extra-byte rejection, uppercase hex, and 17 command-line failures
that make no input or output calls.

The I/O cases check real short reads, Interrupted/data/EOF ordering, host
errors, invalid counts, zero-progress writes, a closed pipe and the shared
attempt budget. The budget case observes two reads followed by 131,070
Interrupted writes, then status 7. Fifty native traces contain no allocation
or descriptor-close calls. A separate real filesystem-limit case observes
an actual three-byte write, a retry of the remaining suffix that returns
EFBIG, status 3, and exactly that output prefix. Its Python OS setup runs
outside the write-only native trace and is not allocation-traced.

### Command and retained evidence

The accepted command ran from the repository root, serialized by the shared
compiler lock, with a 100-second outer timeout and 60-second inner timeout:

```sh
timeout --kill-after=2s 100s flock -E 75 -w 35 target/stdlib-work/library-gpu.lock \
  timeout --kill-after=2s 60s env \
  RUST_MIN_STACK=16777216 LANIUS_GPU_CODEGEN_TEST_TIMEOUT_MS=45000 \
  target/stdlib-build/debug/deps/extended_derive_key_execution-06272c57a353eb16 \
  hkdf_application_matches_rfc_and_independent_binary_models_and_bounds_io \
  --exact --nocapture --test-threads=1
```

The executable basename identifies the accepted local build; a fresh build
may report another basename. Local logs are ignored artifacts under
`target/stdlib-work/sha2-admission/`: `derive-key.log` and
`build-derive-parser-final.log`.

### Trace-parser correction history

The first application gate failed after 5.40 s with zero tests passed. Its
Rust request parser expected exactly `) = `, while strace aligns syscall
results with variable spaces. The driver correction splits at ` = `, trims
the argument suffix, and then removes `)`. The program and cryptographic
oracle did not change. The accepted 51-case result above comes from the
fresh build and rerun after this harness correction.

The original driver and failure log are retained locally as
`derive-driver-trace-parser-original.rs` and `derive-key-trace-parser.log`
in the same ignored admission directory. This history records a test-harness
failure, not a production cryptographic fix.
